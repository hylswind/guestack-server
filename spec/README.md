# Guestack backend specifications

> The formats this repository leads, with machine-readable test vectors for every implementation.

The frontend's login page and the RP SDK conform to these specifications. They pin a tag of this repository and run `spec/vectors/*.json` in their own tests. They never keep an edited copy.

## Test vectors

Vectors live in [`spec/vectors/`](vectors).

| File | Checks |
|------|--------|
| `epoch.json` | `EPOCH_ID` → `[epoch_start, epoch_end)`, invalid IDs |
| `phone.json` | Normalisation of `phone_number`, phone policy, resulting error code |
| `guest-id.json` | Guest ID derivation with all intermediate values |
| `nonce.json` | RFC 7638 thumbprint input, thumbprint, nonce |
| `pop.json` | A valid `pop` and invalid ones that must yield `pop_invalid` |
| `identity-token.json` | Exact header and payload bytes, signing input, a token to verify, DER→raw conversion |
| `issuer-key.json` | A test issuer key as PEM, with the JWK and `kid` derived from it |
| `channel.json` | HPKE requests to decrypt, exact encrypted responses, invalid requests |
| `dev-build.json` | **Not a vector, and not production values.** Dev backend fixtures: the dev attestation root and its SHA-256, dev PCRs, dev Telegram signing keys and client ID, and the dev issuer key |

The vectors are generated by the Go implementation (`make vectors`). Each one has also been recomputed by a separate implementation outside this repository: Python `hashlib`/`hmac`, and a hand-written RFC 9180 key schedule on `cryptography`.

> [!NOTE]
> Signatures and HPKE encapsulations are randomised. For those, a conforming implementation verifies or decrypts the vector and does not try to reproduce its bytes.

## Conventions

| Notation | Meaning |
|----------|---------|
| `b64u` | base64url without padding. Decoders reject padding, characters outside the alphabet, and non-zero trailing bits |
| `‖` | Concatenation |
| `\0` | One zero byte |
| JSON | UTF-8 |
| Times | Unix seconds |

### JSON parsing

Guestack's own formats (the `register` request, the RPC envelope, the JWK, `pop`) must not contain members other than the ones specified, and the backend rejects unknown members.

The backend parses with Go's `encoding/json`. That parser matches member names case-insensitively and takes the last of duplicate members. Conforming senders must not rely on either behaviour.

## Testing against a dev backend

`make run-dev` starts `guestackd` built with `-tags dev` on `127.0.0.1:8080`, serving the current UTC month. It is the same HTTP API and the same document format. Only the trust anchors differ, and they are listed in `dev-build.json`:

- **Login page tests** write a temporary copy of `login.html` whose constants block holds `nitro_root_sha256_hex`, the `pinned_pcrs_hex` (PCR4, PCR7, PCR12), the local API base, and `telegram_client_id`. A stub `Telegram.Login` signs `id_token`s with one of `telegram_keys` (header `kid` and `alg` as listed, `iss` `https://oauth.telegram.org`, `aud` the client ID as a string, `nonce`, and `phone_number` as bare digits). Keep `exp − iat` at 30 s, as Telegram does.
- **RP SDK tests** bundle `issuer_jwk` (with `issuer_kid`) as a test-only issuer key.
- `go run -tags dev ./cmd/devclient` performs one full registration, playing the login page's part, and is a working reference for both.
